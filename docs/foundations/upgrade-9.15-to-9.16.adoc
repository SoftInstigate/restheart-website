RESTHeart 9.16 has three breaking changes. Check each one against your deployment:

* clients send `filter`, `sort` or `sort_by` through ACL permissions: see <<a-read-sends-its-own-query-only-if-its-permission-allows-it>>;
* change streams run under a permission with a `readFilter` or a `projectResponse`: see <<change-streams-do-not-apply-the-readfilter-and-projectresponse>>;
* MCP clients saved the URI of an aggregation, or permissions name an aggregation by its exact `/_aggrs/` path: see <<aggregations-answer-at-_queries-and-mcp-uses-it>>.

== What changed

=== A read sends its own query only if its permission allows it

A filter written by the client can reveal the fields that `projectResponse` hides. A condition on a hidden field tells which documents match it, and a sort on it tells the order of its values. For this reason 9.16 refuses these queries unless the permission allows them.

Before 9.16, a permission that allowed a `GET` also let the client add `filter`, `sort` and `sort_by`.

From 9.16, a `GET` with one of them gets `403`, unless its permission allows it. This applies to `_size` too. The response says:

[source]
----
filter, sort and sort_by are not allowed by this permission: query through an aggregation, or ask for a permission with mongo.allowFilter
----

For each query a client sends, choose one way:

* **An aggregation.** Declare it on the collection and call it with `/coll/_queries/<name>`. The pipeline must apply the caller's `readFilter` itself: see link:/docs/mongodb-rest/aggregations#aggregations-and-permissions[Aggregations and permissions].
* **A choice declared by the permission.** For an order, or an optional condition the client picks by value, the permission is enough: see link:/docs/security/permissions#alternatives[the alternatives a permission declares].
* **`allowFilter` on the permission**, for a role that must write its own queries:

[source,json]
----
"mongo": { "allowFilter": true }
----

To keep the behaviour of 9.15 on every permission, change the default of the mongo service:

[source,yaml]
----
mongo:
  default-allow-filter: true
----

Three things do not change. The root role can always query. The requests a plugin allows through the `ACLRegistry` are not checked. Writes are not affected: a bulk `PATCH` or `DELETE` still needs a filter, and `allowBulkPatch` and `allowBulkDelete` decide about it.

In the MCP catalog, the `query` and `size` actions do not show `filter` to a caller whose permissions do not allow it.

See link:/docs/security/permissions#allowfilter[allowFilter].

=== Change streams do not apply the readFilter and projectResponse

Before 9.16, a change stream added the caller's `readFilter` and `projectResponse` to its stages. A stream with no stages of its own sent each user only the events of the documents the `readFilter` allowed.

From 9.16, a change stream does not do it any more. The stream itself must send each user only their own events. It does it in one of two ways:

* `notify_when` on a `@user` variable;
* a `$match` stage that uses `@user` or `@mongoPermissions`.

A stream under a permission with a `readFilter` that does neither is refused with `403`. Without this check, after the upgrade it would send every event to everyone, with no error. The response says:

[source]
----
this change stream is allowed by a permission with a readFilter, which change streams do not apply since 9.16: segregate the events with notify_when on @user._id, or in the stages, or declare "segregation": "none" for a stream meant for every event
----

Before (9.15), with a `readFilter` of `{"owner": "@user._id"}` on the permission:

[source,json]
----
{ "uri": "mine", "stages": [] }
----

After (9.16):

[source,json]
----
{
  "uri": "mine",
  "stages": [],
  "notify_when": { "fullDocument::owner": { "$var": "@user._id" } }
}
----

The server reads `@user._id` from the caller's account when the stream opens, never from the request. Use the variable the account carries: `@user._id` with MongoDB users, `@user.sub` with a JWT, `@user.userid` with the file realm.

Two more cases:

* a stream that hid fields with the `projectResponse` now hides them with a `$project` stage;
* a stream meant for every event declares `"segregation": "none"`, and is not refused.

See link:/docs/websocket/change-streams#permissions[Change streams and permissions].

=== Aggregations answer at `/_queries/`, and MCP uses it

From 9.16, the suggested path of an aggregation is `/coll/_queries/<name>`. The old path, `/coll/_aggrs/<name>`, still works.

A permission's predicate matches the exact path the client calls. A permission written for `_aggrs` does not allow `_queries`. When an application moves to `_queries`, update its permissions too.

MCP uses `_queries` from 9.16, and this has two effects:

* the URI of an aggregation resource is `.../_queries/<name>`. A client that saved a URI with `_aggrs` gets the new one from `list_apis`;
* an MCP call runs on the `_queries` path. A permission with the exact `_aggrs` path, such as `path('/inventory/_aggrs/byStatus')`, no longer allows it. Use `path-prefix('/inventory')`, or add the `_queries` path.

See link:/docs/mongodb-rest/aggregations[Aggregations].

== What is new

These need no change on your side:

* `mongo.sort` sets the order of the reads a permission allows: see link:/docs/security/permissions#sort[sort].
* A permission can offer the client a few choices, picked by name or by value, with `$ifvar` and with `$var` defaults: see link:/docs/security/permissions#alternatives[the alternatives a permission declares].
* All the clients of a change stream share one MongoDB cursor, whatever their `notify_when` value.
* `notify_when` accepts `@user` variables: see link:/docs/websocket/change-streams#notify-when-user[Events per user].
